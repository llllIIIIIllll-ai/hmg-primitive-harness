## Primitive skill layer

1. Represent verified behaviours as reusable whole-body SKILLS, not task-specific programs.
   A task solution is a short composition of skills, e.g.:
     approach(box); squat(target=box); grasp(box, hands="both"); standup(maintain_grasp=True)
   Each skill has a name that states its mechanism, a fixed signature with named params,
   documented preconditions, postconditions and side effects, and a verified scope.
   Actors create new skills and improve existing ones while solving their task; reusable
   behaviour must not stay buried inside a one-off program.

2. PRIMITIVES.md is the skill catalog. One entry per verified skill:
   - skill name + signature (params, defaults)
   - applicability conditions (object class/geometry/pose, base stance/placement,
     hand availability, required contacts)
   - pinned source hash of the exact verified source
   - verified scope (tasks, seed domains, known failure boundaries)
   - the failure signature it removes
   Keep entries compact; no step-by-step recipes.

3. task_memory.md per task (work/tracks/<task>/task_memory.md), kept current by the actor
   and audited by you:
   - current failure state (what fails now, with the measured signature)
   - disproven hypotheses (what was tested and ruled out, and why)
   - do-not-retry list (configurations/methods already shown not to work)
   - next experiment (the single next thing to try and the measurement that decides it)

4. Promotion: promote a skill only after verifier gate A/B (and C when its scope crosses
   tasks) with the exact source hash pinned. A task success is evidence for the skills it
   used. Prefer the least-specialised skill with the wider verified scope.

5. Composition gap: the server must let a task program call registered skills. If the sandbox
   cannot compose registered primitives, have the fixer add the minimal trusted composition
   mechanism and report the measurement. Do not change physics, reward or predicates.

## Skill consolidation (hard)

A. The deliverable is a SMALL set of reusable skills, not one skill per task. Before a new skill
   is catalogued, check whether an existing skill can be extended to cover it. Prefer extending
   over adding; a duplicated mechanism under a new name is a defect.

B. Cluster skills by MECHANISM (the motion/control loop it implements), CONTRACT (signature,
   preconditions, postconditions, side effects) and APPLICABILITY (object classes, stances,
   contacts, task families) — never by name alone. Variants that implement the same mechanism
   with different constants are ONE skill.

C. For each cluster, define ONE parameterized skill subsuming the variants: the union of their
   parameters, explicit preconditions for the cases it does NOT cover, and one mechanism-bearing
   name. So it can be reused on MORE tasks, not just the ones that produced the variants.

D. A merged skill must be re-verified on the UNION of the variants' verified scopes (gate A on
   each seed domain, gate C on each task in scope) before the variants are retired. Update every
   composition that referenced a variant and re-run it; record the result.

E. Merge-or-justify: if a variant stays separate, record in `library/CORRECTIONS.md` which of
   mechanism/contract/applicability differs enough that merging would require a hidden mode switch.

F. Retire superseded entries from PRIMITIVES.md; move their provenance (verified scope, source
   pin, refutation notes) to `library/CORRECTIONS.md` or `library/skills/archive/`.

G. Report each consolidation round: clusters found, merges applied (old name -> new signature),
   re-verification result, and the before/after skill count.
